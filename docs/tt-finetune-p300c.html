tt-finetune on p300c

The v0.2.1 wheel trains a LoRA on this machine's p300c boards once four kernel headers are patched for the newer host compiler. A 135M model learned to turn English into gozer and tt-smi commands: 0 of 204 held-out requests before tuning, 85 of 204 after.

Held-out exact match
0 → 85 of 204

Base SmolLM2-135M against the same model with a rank-16 LoRA. Unseen phrasings and slot values.

Training speed
0.55 s/step

Median over 1,200 steps, about 225 tokens/s, batch 1, sequence 128, after compile.

Blocker found
Host SFPI 7.96

The wheel's kernels were built for SFPI 7.67. A four-edit header patch removes the failure.

Chips per job
2 (one board)

One job per board, so four chips run two jobs. A job pinned to one chip of a board fails in tt-metal.

The result

The task has 17 commands, each with six English phrasings. Four phrasings per command are in training. The other two, and different lease IDs, ticket IDs and reasons, appear only in the 204-request test set. No test request appears verbatim in the training data.

Exact-match answers on the held-out set

Out of 204 requests. The base model repeats the request back, so its zero is a real zero.

Training loss

Logged every 25 steps over one 1,200-step run. Loss covers the whole text, including the request, which the model cannot predict, so it does not fall to zero.

Score by command

Correct out of 12 held-out requests per command. Commands with one fixed form score highest. Commands that need slots such as a lease ID or a reason score lowest.

A longer run did not help. At 2,000 steps the same rank-16 setup also scores 85 of 204. 102 of the 204 answers differ from the 1,200-step run, with 18 gained and 18 lost, so the score has levelled off near 42% for this data and rank.

Typical misses: the model invents a subcommand (gozer withdraw, gozer reserve), writes gozer where tt-smi was meant, or truncates a lease ID. The run was 1,200 steps, about 1.6 passes over the data. More epochs, a larger rank and loss on the command alone are untried.

Why it failed first, and the patch

The smoke test printed only *** End of error message ***. Running the same probe directly showed the cause. The wheel bundles tt-metal built for SFPI 7.67.0, but tt-metal compiles device kernels with the host compiler in /opt/tenstorrent/sfpi, which is 7.96.0 after this morning's reboot to tt-kmd 2.12.0. That compiler treats warnings as errors and rejects four idioms in the older headers.

Header (blackhole)Old idiomHost compiler says
ckernel_sfpu_exp.h, ckernel_sfpu_exp2.h__builtin_rvtt_sfpiadd_i(src, imm, mod)macro is deprecated, provide iptr operands explicitly
ckernel_sfpu_sigmoid_appx.h, ckernel_sfpu_tanh.hsfpi::lut(vFloat, vUInt, vUInt, vUInt)use of deleted function; pass vLut8si coefficients

The patch (tools/patch_wheel_for_host_sfpi.py) calls the builtin with its explicit operands and loads the coefficients as vLut8si from the same registers, so the generated instructions stay the same. After it, a tiny device add is exact in 5.5 s and tt-finetune doctor --smoke passes. Real training compiled and ran with no further header errors.

Pointing the runtime at an older SFPI through an overlay root has no effect, because tt-metal checks /opt/tenstorrent/sfpi first.

Using more than one chip

One job, many chips
Not supported

The project documents a single P150a and no multi-device training. The job ran on xla:0.

One job per chip
fails

With TT_VISIBLE_DEVICES set to one chip of a p300c pair, tt-metal reports a CUSTOM cluster and asks for a fabric mesh graph descriptor.

Two jobs, one per board
works 0.58 s/step

Each job runs about 6 to 8% slower than the 0.55 s/step solo run, so two boards give about 1.85 times the work. It needs a private temp directory per job (below).

Two shared paths break concurrent jobs

Shared pathWhat happensFix
~/.cache/tt-finetune/workspace (pipeline manifest)One job reads the manifest while another is writing it, gets an empty file, and stops with TypeError: 'NoneType' object is not subscriptable.A workspace= per job.
/tmp/tt_pjrt_system_descriptorThe second job trains all its steps, then fails at checkpoint export with system desc does not exist and Error code: 13. The path comes from tempfile.gettempdir() in ttxla_tools/serialization.py.A private TMPDIR per job. Keep it short, because a long path fails with AF_UNIX path too long.

Evidence for the second row: the shared-/tmp pair failed three times out of three, in the second job each time. With a private TMPDIR for each job, both jobs finished 100 steps and saved adapters. That is one passing pair run, so treat it as likely and not settled. The script is examples/translator/run_two_boards.sh.

How much depends on tt-xla

Python files
195

About 94,000 lines.

12

Plus 5 that mention PJRT and 1 that loads torch_plugin_tt.

Import ttnn
26

132 files reference tt_lang. Most of the code already targets tt-metal and TT-Lang directly.

The wheel itself is a frozen bundle: the PJRT plugin 1.4.0.dev20260723 (TT-MLIR plus its own tt-metal), a custom torch-xla 2.9.0, and tt-lang 1.1.5. Orchard's pinned pair is tt-lang 1.1.10 with tt-metal 0.80. I could not check how actively tt-xla is maintained, because the GitHub token for the Tenstorrent organization is blocked by SSO.

Questions for the author

  1. Host compiler. Can the wheel bundle its own SFPI, or update the four headers, so it builds on current hosts without a patch?
  2. p300c. Is a two-chip board with one active training chip an intended setup? The device open logs TT_FATAL ... connects to a remote mmio device and carries on.
  3. Multi-chip. What is the plan for using more than one chip in a job, and does it go through tt-xla or tt-metal directly?
  4. Concurrent jobs. Would you take a change that puts the pipeline manifest and the system descriptor in a per-run directory? Today two jobs on one host collide on both.
  5. tt-xla. How much of the plan depends on it, and would a ttnn-only backend be accepted?
  6. Next target. We want to LoRA-tune a coder model on TT-Lang kernels. Which model sizes and which architectures are qualified for training today?
